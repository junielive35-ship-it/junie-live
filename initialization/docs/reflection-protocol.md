# Reflection Protocol

Use this file for post-task reflection after valuable work.

## Trigger

Reflect after meaningful tasks, especially code changes, PR reviews, major decisions, incidents, or workflow failures.

## Questions

- Was the task intake clear?
- Was the work decomposed well?
- Was delegated context sufficient but not bloated?
- Did review catch the right issues?
- Did the work reveal product, architecture, tooling, or process friction?
- Did it reveal contradictions between strategy, docs, memory, skills, or operating rules?
- Is there a reusable improvement worth making now?

## Allowed outcomes

- Daily memory note.
- Docs update.
- Checklist/prompt improvement.
- Skill improvement.
- Tooling note or proposed tool change.
- Change candidate requiring approval.

Semantic `MEMORY.md` changes require approval unless explicitly delegated. After each `MEMORY.md` edit, check its size.

Self-simplification may propose `MEMORY.md` changes but should not directly rewrite it.

## Reflection note template

```markdown
## YYYY-MM-DD — Task title

Outcome:
Evidence:
What worked:
What did not:
Reusable improvement:
Applied/proposed changes:
Follow-up:
```
